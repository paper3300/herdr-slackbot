### Bridge flows
- **Commands** return within the 3s ack window. `list`/`status`/usage are answered in the ack. `new`/`send` without args open a modal after the ack. With args, they validate synchronously and do the rest on a worker thread.
- **New agent (D3/D4/naming):** `tab.create` (label `slack-<N> <summary>`, or the given name) → `agent.start` (claude/codex args per SPEC) → thread root `🚀 name · ws` with kind/model/cwd/prompt and a mute button → prompt. `agent_not_ready` at startup → "confirm on PC". `HerdrOutcomeUnknown` → warning, never retried. `StateError` (lost counter) → asks for a name.
- **Modal:** `dispatch_action` on workspace → `views.update` with the new cwd prefill (block_id `cwd:<ws>` so the prefill takes effect). On kind → claude/codex model/effort/permission fields are swapped (codex models from its cache/config). The name is validated in `view_submission` with `response_action: errors`.
- **Send (D5/D6):** `working` → busy, `blocked` → confirm on PC, `unknown` → rejected. A send within 15s of the previous Slack prompt to the same session is also rejected, to avoid double sends before `working` arrives. The first send creates the thread (root = confirmation); later sends reply in the existing thread.
- **Prompt delivery (finding 7):** the pending task is recorded before prompting. On `agent_prompt_stalled` or an unknown outcome, the bridge watches for activity (`state_change_seq`/working) for `STALL_WAIT`. If none, it reads the visible screen: if the prompt text is there, it warns "reached the agent but has not started" and does not resend. It resends exactly once only when the text is provably absent. Codex gets `CODEX_PROMPT_DELAY` after start.
- **Threads (D7/D11):** thread replies in the DM go to the thread's agent session (following pane moves). If the agent exited or the pane now hosts another session, the reply is rejected with a notice. DMs outside a thread get ephemeral usage. A thread that isn't bound to an agent gets a notice.
- **Notifications (D8/D9):** transitions from `SubscriptionManager` go through one ordered notifier thread. `notify.decide_notification` decides started/blocked/completed, and PC agents' threads are created on the first notification. `ended` transitions with a pending Slack task post "⚠️ … ended before completing the Slack task". Results come from Claude JSONL first, then the screen parser, then the raw tail (in a code block). The header is `✅ name · ws · duration`, with cwd and title in the context line.
- **Restart:** `resume_pending` settles pending Slack tasks that finished (result), blocked (alert), or whose agent is gone ("ended" notice). Tasks still working are left for the live transitions.

## Live findings fixed during M2
1. **Prompting right after `agent.start`** can fail with `agent_not_ready: agent X is not an active named agent`. The name only becomes addressable a moment later. For just-started agents the first prompt retries `agent_not_ready`/`agent_not_found` up to 10×1s. Herdr raises these while resolving the target, before writing anything, so no double send is possible.
2. **Codex reports no `agent_session` until its first turn.** A thread for such an agent is keyed provisionally (`pending:<terminal_id>`) and marked `provisional`. It is re-keyed to the real session when a transition or thread reply sees it, checking that the `terminal_id` matches. Resume handles it too. This also covers `send` to a PC-started codex that has not run a turn yet.

## Notes / open points
- Completion and blocked messages are thread replies without `reply_broadcast`, following D7. Whether Slack alerts the user for bot replies in a DM thread depends on their notification settings. If they turn out too quiet in practice, a broadcast option is a small change.
- No real Slack tokens yet, so Slack-side behavior is verified only through bolt dispatch with mocks. Real Socket Mode, `views.update`, and `files_upload_v2` still need a live check once the app exists (M3 manifest).
- The bridge workspace `herdr-slack` is only hidden from the `new` modal here. Creating it and running the bridge from a Herdr startup hook is M3.

**Limits:**
- Reconciliation relies on Slack returning `metadata` with `include_all_metadata`. This is not yet verified live because there are no real tokens.
- If Slack stores a message but history doesn't show it yet when the lookup runs (after the ≥1s backoff), a duplicate is still possible. That is the at-least-once edge case.
- The shared thread lock serializes admission and notifications. That is fine at a single user's volume, but a slow result read delays a concurrent send by that long.
