# M3 — Herdr plugin packaging + setup (D12, D13, D14, D15)

> The sections are chronological. The *Built* table describes the current behaviour. The verification and review-fix sections record each round as it was then: earlier Ctrl+C / pane-reuse behaviour was replaced by the stop request and always-fresh-tab launch ("Recheck fixes", "Recheck2 fixes").

## Herdr 0.8.2 plugin format (verified, not guessed)
Sources: `herdr api schema --output` (`PluginManifest*`, `InstalledPluginInfo`, `PluginInvocationContext`), the installed `herdr-file-viewer` manifest, `%APPDATA%\herdr\plugins.json`, CLI help, and strings in `herdr.exe`.
- `herdr-plugin.toml` at the plugin root. Required fields: `id`, `name`, `version`, `min_herdr_version`. `description` and `platforms` are optional (Herdr warns if `platforms` is missing).
- Tables:
  - `[[build]]` `{command, platforms}`: runs at `plugin install`.
  - `[[startup]]` `{command, platforms}`: event `plugin.startup`, runs when the **server starts**. It does **not** run on `plugin link`.
  - `[[actions]]` `{id, title, description, command, platforms, contexts}`.
  - `[[events]]` `{on, command, platforms}`.
  - `[[panes]]`, `[[link_handlers]]`.
- **No keys in the manifest.** Keys go in the user's `config.toml` as `[[keys.command]] type = "plugin_action"`, `command = "<plugin>.<action>"`.
- Plugin command env includes `HERDR_PLUGIN_ROOT`, `HERDR_PLUGIN_CONFIG_DIR`, `HERDR_PLUGIN_STATE_DIR`, `HERDR_PLUGIN_ACTION_ID`, `HERDR_PLUGIN_EVENT(_JSON)`, `HERDR_PLUGIN_CONTEXT_JSON`, `HERDR_SOCKET_PATH`. Paths are reported with the `\\?\` prefix, so they are stripped.
- `plugin action invoke` returns immediately (`status: running`). stdout/stderr/exit code are in `herdr plugin log list`.
- On Windows, `pane process-info` reports the **pane shell** as the foreground process even while a child (python) runs. The bridge pane can't be recognized that way, so the bridge records its own identity. Pane occupancy is judged from the shell's child processes. See "Review fixes" below.

### Bridge startup behavior (`__main__.py`)
- Missing tokens: prints a "not configured yet" message with the next steps and exits 2.
- Slack auth or connection failure (`BoltError`, `SlackApiError`, `SlackClientError`): prints one redacted line and a hint, exits 2, and does not retry.
- Writes `STATE_DIR\bridge.runtime.json` (see "Review fixes"; this replaces the original `bridge.pane`).
- stdout/stderr are set to `errors="replace"`, and pipes use UTF-8. Before this, `check` crashed on emoji labels with cp949.

## Recheck fixes (docs/review/M3-recheck.md)

The guiding change is **one mutex**: `STATE_DIR\lifecycle.lock` (the OS file lock, `plugin.lifecycle_lock`) is held across the whole check → act sequence of launch, stop and restart. The child bridge also holds it for its handoff: check its reservation → take the instance lock → look up its pane → write `bridge.runtime.json` → ack. Under the mutex the state is always exactly one of stopped / starting / running.

| # | Fix | Regression tests (`tests/test_plugin.py`) |
|---|---|---|
| R1 | **Stop never types into a terminal.** After verifying the lock holder's pid and creation time, stop writes `stop.request` = {pid, start}. The bridge's main loop checks it every second and shuts down only if the request is addressed to its own pid and creation time. There are no pane lookups and no `send-keys`, so a bridge that exits mid-stop can't cause input into its old terminal. The terminate fallback is unchanged: it re-verifies the pid and creation time first. Stale requests are cleared on bridge start (inside the mutex) and on exit. | `test_stop_sends_an_addressed_request_and_never_types` (zero CLI calls), `test_r1_bridge_exit_during_stop_puts_nothing_into_its_old_terminal`, `test_stop_request_is_only_honoured_by_its_addressee`, `…_rechecks_the_process_before_terminating`, `…_terminates_a_verified_bridge_that_ignores_the_request`, `test_restart_stops_then_launches_in_the_same_idle_pane` |
| R2 | **Fresh tab by default.** The previous bridge pane is reused only if the earlier checks pass (same server and terminal, shell in the foreground, no agent, no child processes) **and** `herdr pane read` ends with a bare default prompt line (`PS …>` for PowerShell, `X:\…>` for cmd, `$`/`#`/`%` for sh-family shells). This is the review's "starting → stop → running" observation. | `test_r3_child_ack_cannot_fall_between_launch_checks` (the review's interleaving: the child's ack waits for the launcher), `test_stop_while_starting_cancels_the_start`, `test_run_with_a_cancelled_launch_id_does_not_start` |
