## 1. Retry through the CLI can repeat an already executed mutation

- **Severity:** major
- **Location:** `herdr_slackbot/herdr_client.py:128`, `herdr_slackbot/herdr_client.py:333`
- **Problem:** EOF after sending a request raises the same `HerdrUnavailable` exception as failure to open the pipe. `AutoTransport` retries both through the CLI, including mutating requests.
- **Failure scenario:** Herdr accepts `agent.prompt` or creates a tab, then the connection closes before its reply arrives. The bridge submits the same operation again. A fake pipe that accepts the write and returns EOF reproduces a second `agent.prompt` call through the CLI.
- **Suggested fix:** Distinguish failure before submission from an unknown outcome after submission. Fall back automatically only when the request was not sent, or when replay is safe for that method. Reconcile uncertain mutations instead of resending them blindly. Add a test asserting that EOF after a mutation write does not invoke the CLI.

## 2. Snapshot seeding can run ahead of buffered status events

- **Severity:** major
- **Location:** `herdr_slackbot/events.py:256`, `herdr_slackbot/events.py:265`
- **Problem:** `_subscribe()` opens a stream, obtains a newer snapshot, updates `_status`, and queues a synthetic transition before starting the stream reader. Older events already buffered on that stream are subsequently applied to the newer state. Comparing only status strings does not reject them. Resync also changes `_status` outside the dispatcher, so single-threaded callbacks do not establish a consistent state order.
- **Failure scenario:** A previously working pane reconnects. It becomes blocked and then done between opening the subscription and reading the snapshot. Replaying those buffered events after the done snapshot produces `working -> done` (synthetic), `done -> blocked`, and `blocked -> done`: a stale confirmation alert and duplicate completion for one turn. This sequence was reproduced.
- **Suggested fix:** Serialize snapshot reconciliation and event application through one state owner, with a defined snapshot/event boundary. Track revisions or `state_change_seq` where available, and subscription generations, so events covered by a snapshot cannot move state backward. Add a deterministic test buffering blocked/done during subscription setup and assert one completion with no obsolete blocked alert.

## 3. Queued status events can be attributed to a replacement session

- **Severity:** major
- **Location:** `herdr_slackbot/events.py:218`, `herdr_slackbot/events.py:223`, `herdr_slackbot/events.py:235`
- **Problem:** The manager remembers status by pane only and resolves the session with `agent.get` when dispatching each event. It retains no session identity for the previous status or queued event. Agent detection also returns immediately for an already subscribed pane, without checking whether its session changed.
- **Failure scenario:** Session A finishes and its done event waits in the queue. Before dispatch, session B starts in the same pane. The manager emits A's completion with B's session and metadata, potentially posting to B's thread or clearing B's pending task. A reproduction emitted `status=done` for session B while its attached live metadata said `agent_status=working`.
- **Suggested fix:** Track session identity alongside each pane's status and subscription generation. Reconcile replacement sessions explicitly and invalidate old queued transitions; never transfer the old session's previous status to the new session. Since status events omit session IDs, handle identity ambiguity conservatively using cached identity and lifecycle/snapshot verification. Add a same-pane A-to-B replacement test with queued A events.

## 4. Replayed exit/close/move events tear down live subscriptions

- **Severity:** major
- **Location:** `herdr_slackbot/events.py:202`
- **Problem:** Only agent-detected lifecycle events receive live-state verification. Exit, close, and the old side of move events unconditionally unsubscribe and forget status, although the lifecycle stream replays retained history.
- **Failure scenario:** After reconnect, a retained `pane_exited` event from an earlier terminal lifetime arrives for a pane now running another agent. The manager drops that live subscription and its working state. A reproduction left both the subscribed set and known status empty despite the fake client's live working agent. Completion during the gap can be lost; the next resync seeds done without a previous working state.
- **Suggested fix:** Verify destructive lifecycle hints against current agent identity/state or a revision watermark before removing anything. Apply this to exit, close, and move events. Extend the replay test to cover a stale destructive event targeting a currently live pane; its current closed-pane-only case cannot expose the bug.

## 5. A transient metadata error permanently consumes a completion

- **Severity:** major
- **Location:** `herdr_slackbot/events.py:222`, `herdr_slackbot/events.py:347`
- **Problem:** `_on_status()` commits the new status before resolving metadata. `_safe_find()` converts every Herdr error into `None`, so a transient failure produces a transition without an agent session. Later duplicate status events are discarded, and resync does not reconcile status for healthy subscriptions.
- **Failure scenario:** `agent.get` temporarily fails while processing working-to-done. The callback receives no session with which to locate the required thread. After connectivity recovers, repeating done and running resync produces no usable replacement transition. The isolated reproduction yielded only `(done, None)`.
- **Suggested fix:** Distinguish an absent agent from a failed lookup. Preserve known session metadata and retry unresolved transitions instead of marking them fully handled. Reconcile unresolved status/metadata even when the stream remains open. Test one failed lookup followed by recovery and require exactly one completion with the correct session.

## 6. Shutdown races with in-flight subscription creation

- **Severity:** major
- **Location:** `herdr_slackbot/events.py:158`, `herdr_slackbot/events.py:251`, `herdr_slackbot/events.py:282`
- **Problem:** `stop()` closes only the subscriptions currently registered. An in-flight `_subscribe()` or `_open_lifecycle()` can publish another stream afterward because neither checks the stopped state when installing it. Dispatcher, resync, and reader threads are not joined.
- **Failure scenario:** A resync blocks while opening a pipe; `stop()` clears the registered streams and returns; the open then succeeds and installs a live reader. A barrier-controlled reproduction left `{'w1:p1'}` subscribed with an unclosed stream after stop. Restarting the same manager can also overlap old workers because `start()` clears the shared stop event before they have necessarily exited.
- **Suggested fix:** Make stream installation conditional on the active manager generation under the lock, closing any stream opened for a stopped generation. Coordinate shutdown with in-flight creation and join workers before allowing restart, handling calls from a worker without self-joining. Add stop-during-open and stop/start tests that assert no surviving old streams or callbacks.

## 7. Failed persistence leaves the in-memory state changed

- **Severity:** major
- **Location:** `herdr_slackbot/state.py:126`, `herdr_slackbot/state.py:132`
- **Problem:** State mutators change `_data` before `_save()`. If the atomic write fails, the exception propagates but the mutation remains visible in memory. A later unrelated save can persist an operation that previously reported failure. Atomic file replacement does not make the store operation transactional.
- **Failure scenario:** All Windows sharing-violation retries fail while clearing a pending task. The running bridge sees the task as cleared while disk still contains it; restart can produce a duplicate completion. The inverse operation was reproduced: failed `set_pending_task()` left a task in memory and `None` on disk.
- **Suggested fix:** Build a candidate copy under the lock, write it successfully, then replace `_data`, or restore the previous state on every save failure. Apply this consistently to insert, update, removal, and counter operations. Inject write/replace failures and assert both disk and memory retain the last committed state, including after a later successful mutation.

## 8. Corruption recovery reuses automatic agent numbers

- **Severity:** major
- **Location:** `herdr_slackbot/state.py:84`
- **Problem:** An unreadable state file is backed up and replaced logically with a counter of zero. This violates D4's explicit monotonic, never-reused numbering requirement. The existing corruption test explicitly expects the reset behavior.
- **Failure scenario:** After `slack-1` has been allocated, damage the state JSON and reopen the store. The next allocation returns 1 again; this was reproduced. Previously allocated names can be reused even if they no longer appear in the live agent list.
- **Suggested fix:** Recover a durable high-water mark from a verified backup/journal, or stop automatic name allocation until that value can be recovered. Do not silently restart at zero when an existing state file is corrupt. Replace the current corruption test with a recovery/failure test that proves an issued number cannot be reissued.

## 9. Muting suppresses a blocked notification required by D9

- **Severity:** major
- **Location:** `herdr_slackbot/notify.py:75`
- **Problem:** `decide_notification()` suppresses blocked transitions for muted PC-originated work. `SPEC.md` explicitly requires blocked notifications for all agents. The milestone's open question does not change that requirement, and the existing muted-PC test codifies the deviation.
- **Failure scenario:** A user mutes completion notifications for a PC agent; that agent later needs permission. The decision is `none`, so the user receives no request to confirm on the PC.
- **Suggested fix:** Apply mute suppression to PC completion notifications while retaining blocked alerts under the current spec. Update the muted blocked test to expect `Action.BLOCKED`.

## 10. PC completion notifications include a transition excluded by D9

- **Severity:** minor
- **Location:** `herdr_slackbot/notify.py:91`
- **Problem:** The PC branch accepts every previous status in `ACTIVE`, including blocked, while D9 specifies `working -> done` only. The existing blocked-to-done test enforces the broader behavior noted as an open question in the milestone report.
- **Failure scenario:** A PC agent goes directly from blocked to done after cancellation or confirmation. The bridge emits a result notification even though the required transition was not observed.
- **Suggested fix:** Require `prev == 'working'` in the PC completion branch. Keep Slack pending-task completion rules separate and update the PC blocked-to-done test to expect no notification.

## 11. Caller-owned dictionaries bypass the state lock and persistence

- **Severity:** minor
- **Location:** `herdr_slackbot/state.py:126`, `herdr_slackbot/state.py:149`
- **Problem:** `entry.update(fields)` retains nested mutable objects supplied by the caller. Returned state is deep-copied, but incoming task data is not. Callers can therefore mutate the store without its lock or a save.
- **Failure scenario:** Pass a task dictionary to `set_pending_task()`, then set `task['working_announced'] = True`. The store immediately reports true while a freshly loaded store does not; this was reproduced. Concurrent caller mutations can also occur during serialization.
- **Suggested fix:** Deep-copy incoming fields before retaining them, under the store lock. Add a test that mutates nested input data after a successful write and verifies that both the store and persisted data remain unchanged.

## 12. A PID-file write failure leaks the acquired instance lock

- **Severity:** minor
- **Location:** `herdr_slackbot/state.py:177`
- **Problem:** After taking the OS lock, `acquire()` stores the handle and writes `bridge.pid` without cleanup on failure. If `__enter__()` raises, Python does not invoke `__exit__()`.
- **Failure scenario:** On Windows, `bridge.pid` is read-only or held with incompatible sharing permissions. Acquisition raises, but a retained lock object continues holding `bridge.lock`; a retry reports `AlreadyRunning` even though startup failed. Injecting a PID write failure reproduced this behavior.
- **Suggested fix:** Release and close the lock handle, and clear `_fh`, if PID publication fails. Add a fault-injection test requiring another instance to acquire immediately after the failed attempt.

## 13. Notice removal silently deletes legitimate indented output

- **Severity:** minor
- **Location:** `herdr_slackbot/parser.py:105`, `herdr_slackbot/parser.py:154`, `herdr_slackbot/parser.py:197`
- **Problem:** `_is_notice()` identifies any nonblank line with at least 40 leading spaces as a UI notice. This filter runs over the entire Claude response and the raw fallback, including Codex output. Indentation alone does not distinguish UI from answer content.
- **Failure scenario:** A code block contains a continuation aligned 42 spaces from the left, such as `important_call()`. Structured parsing deletes that line and leaves an empty code block; the Codex fallback also deletes it. Both cases were reproduced. D10's raw fallback consequently loses nonblank response content.
- **Suggested fix:** Match known notice text in its expected UI region rather than removing all deeply indented lines. Preserve code and unknown output. Add structured and fallback cases with deeply indented code alongside a real update notice.
