## 1. Herdr calls run before acknowledgment and can expire modal triggers

- **Severity:** major
- **Location:** `herdr_slackbot/slack_app.py:72`, `herdr_slackbot/slack_app.py:83`, `herdr_slackbot/slack_app.py:91`; `herdr_slackbot/bridge.py:355`
- **Problem:** Commands call `handle_command()` before `ack()`. List/status and direct new/send perform synchronous Herdr requests there. View submissions likewise query live agents/workspace labels before acknowledging or returning modal errors. Those requests have no deadline that guarantees Slack's response window. The modal-opening paths acknowledge first but still fetch Herdr data before exchanging the short-lived trigger.
- **Failure scenario:** A fake `list_agents()` taking 3.4 seconds made actual Bolt dispatch return HTTP 404 at about 3.01 seconds and log that `on_command` did not acknowledge. Direct new/send may subsequently execute despite the visible timeout, inviting a user retry. Slow workspace/pane reads can similarly prevent a new/send modal from opening. Slack requires acknowledgment within three seconds and prompt use of the modal trigger. See [Slack acknowledgment guidance](https://docs.slack.dev/tools/bolt-python/concepts/acknowledge/) and [Bolt's modal-opening example](https://docs.slack.dev/tools/bolt-python/reference/).
- **Suggested fix:** Acknowledge commands before remote I/O and deliver their results asynchronously. Restrict pre-ack modal validation to bounded local/cached checks, retaining `response_action: errors` for those checks. Open a loading/cached modal immediately, then fetch data and update it. Add latency and Herdr-failure tests using default Bolt response processing, not only synchronous recording bridges.

## 2. Send admission and thread creation are not atomic

- **Severity:** major
- **Location:** `herdr_slackbot/bridge.py:510`, `herdr_slackbot/bridge.py:541`, `herdr_slackbot/bridge.py:593`
- **Problem:** The pending-task/status check happens before a worker is queued. The worker never repeats admission under the session lock; `deliver_prompt()` only locks while unconditionally replacing pending state. Thread lookup/root creation also happens outside that lock. The fifteen-second guard therefore does not prevent two requests admitted before either worker starts.
- **Failure scenario:** Queue two `send coder ...` requests while coder is idle, then run the queued workers. Both prompts are submitted, including the second after the first has changed live status to working. This was reproduced without simultaneous threads. A separate two-thread reproduction produced two Slack roots and two prompts for one session, with only one root retained in state; replies in the orphaned root lose their binding.
- **Suggested fix:** Reserve a task and establish/reuse the root under one canonical session/terminal lock, rechecking admission at worker execution time. The second worker must see the reservation and reject before posting or prompting. Use the same admission path for slash sends, modal sends, thread replies, and initial prompts. Add queued-worker and simultaneous-root-creation tests; current `SyncExecutor` tests hide this window.

## 3. A queued thread reply can be sent to a replacement agent

- **Severity:** major
- **Location:** `herdr_slackbot/bridge.py:565`, `herdr_slackbot/bridge.py:587`, `herdr_slackbot/bridge.py:596`
- **Problem:** D11 session validation occurs in the event handler, but delivery occurs later using a reusable agent name or pane ID. `deliver_prompt()` does not verify that the target still belongs to the expected session or provisional terminal before writing input. Direct sends have the same stale-agent snapshot problem.
- **Failure scenario:** A thread is bound to session A named `coder`. Its reply passes validation and waits in the executor. A exits and B takes the same name/pane. Running the queued job prompts B while recording the task under A. The reproduction sent `bound to A` to a live target whose session was B.
- **Suggested fix:** Resolve and validate the expected session/terminal again immediately before delivery and before any retry. Reject a changed identity and route the notice to the original thread. Prefer a session-addressed or conditional API operation if supported, so target reuse cannot defeat the check. Test replacement between handler admission and worker execution for both named and unnamed agents.

## 4. Unknown prompt outcomes are retried without proof of non-delivery

- **Severity:** major
- **Location:** `herdr_slackbot/bridge.py:218`, `herdr_slackbot/bridge.py:648`, `herdr_slackbot/bridge.py:653`
- **Problem:** `_read_visible()` converts a Herdr read failure into an empty string. The stall handler interprets any screen lacking the prompt's last 24 characters as proof nothing arrived, then resends. Even a successful viewport read cannot prove non-delivery: input may be partially pasted, clipped, cleared, or outside the viewport. This is a new retry in the M2 orchestration layer, independent of the corrected M1 transport behavior.
- **Failure scenario:** The first prompt is accepted but its reply is lost. Activity verification is inconclusive and the visible read fails. The bridge sends the prompt again; a reproduction with `HerdrOutcomeUnknown` followed by a failed visible read produced two submissions. A partial paste missing the final probe also takes the resend path, potentially combining duplicate input.
- **Suggested fix:** Keep an unknown/stalled outcome uncertain unless Herdr provides authoritative evidence that no input was written. Distinguish unreadable screen data from a valid read, and never use viewport absence alone to authorize a mutation retry. Keep safe pre-submission `agent_not_ready` retries separate. Replace the current tests that expect an automatic resend on an empty screen with failed-read, clipped-prompt, and partial-paste cases asserting one submission.

## 5. A delayed completion can clear a newer task's pending state

- **Severity:** major
- **Location:** `herdr_slackbot/bridge.py:235`, `herdr_slackbot/bridge.py:594`, `herdr_slackbot/bridge.py:735`, `herdr_slackbot/bridge.py:757`
- **Problem:** Pending work is identified only by session. After fifteen seconds, a new send is accepted whenever the live status is settled, even if the previous completion has not reached the notifier. The new prompt overwrites `pending_task`; an older queued transition then uses and clears that newer task. Neither transition time nor a task/sequence boundary is checked.
- **Failure scenario:** Task A has run for a minute and is now done, but its valid completion waits in the notifier queue. Send B: live status and the expired grace period permit it. Process A's completion afterward: it reads B's pending record, posts a result, and clears B while B is working. The reproduction showed `prompt='NEW TASK'` becoming `pending_task=None` with live status still working. B can then lose its required completion, especially when muted or finishing in idle.
- **Suggested fix:** Associate reservations and completion processing with a task identity and sequence/time boundary. Do not replace unresolved pending work solely because a grace interval elapsed; reconcile its completion first. Clear pending state only if it is still the exact task being completed. Add a test delaying A's notification until after an attempted send of B. This does not depend on incorrect M1 transitions.

## 6. Provisional migration can adopt an unrelated ended session

- **Severity:** major
- **Location:** `herdr_slackbot/bridge.py:273`
- **Problem:** `_transition_key()` accepts a provisional migration when either terminal ID is missing. Ended transitions intentionally carry `info=None`, so they satisfy the migration condition without proving that their session belongs to the provisional terminal. Migration happens before `handle_transition()` checks `t.ended`.
- **Failure scenario:** An ended transition for old session A is queued. A session-less Codex B starts in the same pane and gets a provisional thread with terminal ID NEW and a pending prompt. Processing A's ended transition rekeys B's thread to A and clears B's task as ended. A reproduction changed the sole state key from `pending:new-terminal` to `OLD` and set its pending task to `None`.
- **Suggested fix:** Require positive terminal identity evidence before adopting a provisional entry. An ended transition with no live metadata must not migrate an unrelated provisional thread; handle it only against its already-bound session. Verify live identity when needed, or defer migration. Add a test with an old ended event and a new provisional terminal in the same pane.

## 7. Codex's mute button still writes to the obsolete provisional key

- **Severity:** minor
- **Location:** `herdr_slackbot/bridge.py:269`, `herdr_slackbot/bridge.py:281`, `herdr_slackbot/bridge.py:690`
- **Problem:** Rekeying the state does not update the root message's mute-button value or leave a resolvable alias. `toggle_mute()` trusts the button's old key and calls `set_muted()`, which creates a new entry if that key no longer exists.
- **Failure scenario:** Start a session-less Codex, allow its thread to migrate to REAL, then click the original root's Mute button. The UI changes to Unmute, but REAL remains unmuted and a new `pending:...` entry is created. This was reproduced, so future PC-originated notifications continue despite the user's mute action.
- **Suggested fix:** Resolve controls by their persisted channel/thread binding to the current session, maintain a safe old-key alias, or update the root control when migration succeeds. Do not create an unbound thread entry from a stale button. Add migration-then-mute/unmute tests for both transition-driven and restart-driven migration.

## 8. Restart resume can post the same completion twice

- **Severity:** major
- **Location:** `herdr_slackbot/bridge.py:173`, `herdr_slackbot/bridge.py:788`, `herdr_slackbot/bridge.py:798`
- **Problem:** Startup runs the notifier before `resume_pending()`. Resume takes an unlocked copy of entries and computes its decision before acquiring the session lock. If the notifier has already completed and cleared the task, resume still acts on its stale pending copy. The lock serializes the posts but does not deduplicate them.
- **Failure scenario:** Pause resume's live lookup for a pending task while a valid working-to-done transition is handled. The notifier posts the result and clears pending. Release resume's lookup: resume posts the result again using the old entry. A barrier-controlled reproduction produced two completion messages in the same thread.
- **Suggested fix:** Under the session lock, reload the current entry and verify the same pending task still needs settlement before choosing an action. Coordinate startup recovery with the notifier, or give both an idempotent task-completion operation. Add an interleaved resume/live-transition test rather than testing resume only against a passive fake manager.

## 9. Transient Slack failures permanently drop live notifications

- **Severity:** major
- **Location:** `herdr_slackbot/bridge.py:711`, `herdr_slackbot/bridge.py:718`, `herdr_slackbot/bridge.py:782`
- **Problem:** The notifier removes a transition from its queue, then logs and discards it if Slack posting fails. There is no retry/outbox or periodic reconciliation of undelivered notifications. Keeping a Slack task pending in state is insufficient because `resume_pending()` runs only at startup and a settled agent need not generate another transition.
- **Failure scenario:** Slack temporarily rejects the completion post. When Slack recovers, the agent remains done, the queue is empty, and no result is delivered until a manual restart or unrelated future activity. Fault injection reproduced zero posts, an empty queue, and a still-pending task after recovery. PC-originated completions have no pending-task recovery path at all.
- **Suggested fix:** Persist or retain failed notification work and retry transient failures with backoff, including rate-limit handling. Track successful delivery per task/transition so retries do not duplicate an already accepted message. Add failure-then-recovery tests proving eventual delivery without an agent status change or bridge restart.

## 10. Exception tracebacks bypass token redaction

- **Severity:** major
- **Location:** `herdr_slackbot/__main__.py:25`
- **Problem:** `RedactSecrets.filter()` sanitizes only `record.getMessage()`. Python's formatter subsequently appends `exc_info`/cached `exc_text`, which the filter never inspects. The bridge uses `log.exception()` in background, notifier, and Slack failure paths, so token-bearing exception messages can reach both stdout and `bridge.log` unchanged.
- **Failure scenario:** An exception includes a Slack token, for example inside an SDK response or echoed input. Logging it with `logger.exception('background task failed')` through the configured filter leaves the token in the traceback. This was reproduced using only the fabricated token `xoxb-FAKE-REVIEW-TOKEN`.
- **Suggested fix:** Redact the final formatted output, including exception and stack text, for both handlers. Keep the existing message/argument protection. Add tests for formatted exceptions and chained exceptions with fabricated bot/app tokens, asserting the rendered output contains no token.

## 11. Quoted Windows cwd arguments are split at spaces

- **Severity:** minor
- **Location:** `herdr_slackbot/commands.py:11`, `herdr_slackbot/commands.py:55`
- **Problem:** The tokenizer recognizes quotes only when they begin a token. In the advertised `key=value` syntax, `cwd="... ..."` begins with `cwd=`, so the `\S+` branch stops at the first space and leaves the quote inside the cwd value. Remaining path text becomes part of the prompt.
- **Failure scenario:** Parsing `Main cwd="D:\My Project" inspect files` produced cwd `"D:\My` and prompt `Project" inspect files`. The new-agent flow passes that broken path to `tab.create`, causing a launch failure or an incorrect working directory/prompt. Paths with spaces are common on Windows.
- **Suggested fix:** Support quoted values inside recognized `key=value` options while preserving Windows backslashes and the original prompt remainder. Reject unmatched quotes rather than silently splitting them. Add tests for `cwd="D:\My Project"`, quoted workspace labels, and multiline prompts.
