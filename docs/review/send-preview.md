# Send modal response preview review

Reviewed `fddeeb099a83036beb321461608503d2c1770925` (`feat: last response preview in send modal`), the `HEAD` captured at review start. All source locations refer to that commit.

**Result: 0 blockers, 2 major findings.** The preview can delay submission acknowledgement, and stale selection events can replace the current preview despite hash checks.

Validation: **567 passed, 5 skipped** with `python -m pytest -q` in an isolated `git archive` extraction. Additional probes used real Bolt dispatch, real threads, deferred workers, a hash-enforcing fake Slack transport and fake Herdr data. No live Slack calls or mutating Herdr commands were made. Source and repository tests were not edited; only this review was added to the checkout.

## Major findings

### S1 — A slow preview update prevents Send from being acknowledged

- **Location:** `herdr_slackbot/bridge.py:1057`–`1063`, `:1074`–`1075`; also `:966`–`974` and `:997`–`1026`. Submission handler: `herdr_slackbot/slack_app.py:81`–`86`.
- **Problem:** Preview workers hold the global `_send_lock` across the network call to `views.update`. `submit_send_view()` must acquire that same lock to remove its preview record, before validation and before the handler calls `ack()`. The existing bounded agent check cannot bound this earlier lock wait. Placeholder updates, and record reconstruction after restart, also perform I/O under this lock.
- **Realistic failure:** The owner finishes typing and clicks Send while a preview's Slack request is slow or waiting to time out. Submission waits for that unrelated request and misses Slack's three-second response window. The lock is shared across views, so a slow preview in another modal has the same effect. Validation and send scheduling can subsequently proceed after the UI has reported a submission failure. Slack requires a timely response to modal submissions; see [modal response timing](https://docs.slack.dev/surfaces/modals/).
- **Reproduction:** Open a preselected-agent modal with `make_env(..., executor=DeferredExecutor(), start=False)`. Run its queued preview on a real thread and block the fake `transport.update_view` on an event. Dispatch a valid `view_submission` through the real Bolt app with default processing. Observed **3.000 seconds**, response **404 / `unhandled request`**, and the modal record still present: submission had not passed the lock. Releasing the preview lets submission remove the record and continue. All agent and Slack operations were fake.
- **Fix direction:** Keep preview bookkeeping locks short and independent of the submission acknowledgement path. Perform network/Herdr work outside that lock, with appropriate per-view generation/hash checks around updates. Add a regression that holds a preview update longer than three seconds while submitting the same or another view, and verifies timely acknowledgement and a single accepted send.

### S2 — Retrying an old selection with the latest hash defeats stale-result protection

- **Location:** `herdr_slackbot/bridge.py:1010`–`1017`, `:1057`–`1063`; `herdr_slackbot/slack_app.py:95`–`98`.
- **Problem:** Sequence numbers reflect handler processing order, not user selection order. The handler passes only `body["view"]`, discarding the action timestamp. An older selection processed after a newer one overwrites `rec.target`, `rec.prompt` and `rec.seq`. When its old hash is rejected, the placeholder update retries with the record's current hash. Its worker then passes the sequence check and publishes the older agent's response.
- **Realistic failure:** The owner quickly selects Alpha and then Beta before a placeholder update completes. Concurrent delivery/handler scheduling processes Beta first and Alpha second. The final preview describes Alpha while the latest user selection is Beta. This can mislead the owner into sending a follow-up such as “yes, apply that change” to Beta based on Alpha's answer. Preserving Slack's selected input does not preserve the correctness of the surrounding preview.
- **Reproduction:** Use two real Bolt `block_actions` payloads with selection timestamps `100.0` (Alpha) and `100.1` (Beta), both carrying the original view hash `h1`. Process Beta, drain its deferred preview, then process the delayed Alpha payload and drain again. A fake transport rejects every non-current hash. Observed update hashes **`[None, h1, h2, h1, h3, h4]`**: the delayed `h1` is rejected, but the retry with `h3` succeeds. Final bridge target and published preview are **Alpha**, although the latest user selection was **Beta**. The rebuilt payload also carries the older prompt snapshot; actual typed-input loss was not established.
- **Fix direction:** Preserve interaction ordering information and reject older/duplicate selection events before modifying the record. Retry a hash conflict only after establishing that the interaction still represents the latest selection; possession of a newer cached hash alone is insufficient. Cover reversed selection-event processing as well as reversed worker completion. Slack documents hashes as protection against outdated view updates: [modal update race handling](https://docs.slack.dev/surfaces/modals/#avoiding-race-conditions-when-using-the-viewsupdate-method).

## Minor observations

- **Raw code fences:** `last_response_blocks(..., markdown=False)` wraps text in a new fence without repairing embedded fences. A raw tail containing one opening triple-backtick fence produces three fence delimiters, so a Codex/terminal tail containing unfinished Markdown can render incorrectly (`blocks.py:419`). The section limit and escaping still hold.
- **Bare mention parsing:** Preview mrkdwn omits `verbatim: true`, leaving automatic parsing enabled for strings such as bare `@here`/`@everyone` (`blocks.py:114`, `:429`). Set it explicitly for strict no-mention rendering. Explicit `<!...>` tokens are escaped correctly; notification behavior in a private modal was not verified. See [Slack automatic parsing](https://docs.slack.dev/messaging/formatting-message-text/#automatic-parsing).

No live Slack modal was opened. Rendering, typing during updates and notification behavior were assessed through code, payloads and official documentation rather than a signed-in client.
