## Findings

### 1. Stop/restart can send Ctrl+C to a pane on the wrong server

- **Severity:** major
- **Location:** `herdr_slackbot/plugin.py:140`, `herdr_slackbot/plugin.py:253`, `herdr_slackbot/plugin.py:279`
- **Problem:** The shared state directory records only a pane ID and PID. `stop()` checks that the runtime lock is held, then accepts any successful `pane get` through the action caller's CLI connection as proof that the saved pane hosts that process. It records and verifies neither the owning Herdr server/socket nor terminal/process identity. `status` likewise presents the saved pane without checking its association with the running process.
- **Concrete failure scenario:** A bridge runs on named server A. An action invoked on server B uses the same plugin config/state directory, and B has an unrelated pane with the same ID. Stop sends Ctrl+C to B's pane, waits 15 seconds, then terminates A's PID. Restart can subsequently start the bridge on B. A fake-server reproduction with a real held instance lock and an A-owned pane record produced `pane send-keys wE:p1 ctrl+c` through B before invoking the termination callback. This requires separate servers; merely attaching another client to A is not this failure.
- **Suggested fix:** Persist an atomic runtime identity containing the owning server/socket, terminal identity, PID and process creation identity. Route control to that server and verify the association before sending input or terminating a PID. Refuse ambiguous ownership. Test mismatched servers, stale records, pane moves/replacement, and process exit/replacement during the stop wait.
- **Stale-ID qualification:** Herdr's installed skill says closed pane IDs are not reused within a live session. A stale file alone does not cause Ctrl+C here: stop returns when the lock is free, and a missing pane falls back to PID termination. Those guards do not establish ownership of an existing pane on another server, or protect the check-to-input interval.

### 2. Launch types its command into an existing pane without checking its occupant

- **Severity:** major
- **Location:** `herdr_slackbot/plugin.py:237`, `herdr_slackbot/plugin.py:247`
- **Problem:** When the workspace exists, launch selects the saved pane if present, otherwise the first pane. `pane_shell()` only determines quoting syntax. No check establishes that the pane is still reserved for the bridge and at an available shell prompt before `pane run` sends text and Enter.
- **Concrete failure scenario:** After a missing-token exit, the user starts an agent or editor in the remaining shell. A later start/restart types the Python launch command into that program. The same happens if the bridge pane was closed and the first remaining pane hosts other work, or an existing workspace already has the configured label. On Windows the reported foreground process can still be PowerShell while a child runs, so the current process-info call is not an occupancy check. The fake CLI trace confirmed that launch proceeds directly from workspace/pane enumeration and shell identification to input, without an ownership or agent check.
- **Suggested fix:** Reuse a pane only when its identity and shell availability are positively established. Otherwise create a dedicated new tab with `--no-focus`, or report the conflict. Add occupied-saved-pane and occupied-fallback-pane cases. Workspace label equality alone should not authorize terminal input.

### 3. Concurrent starts are not idempotent before the bridge acquires its lock

- **Severity:** major
- **Location:** `herdr_slackbot/plugin.py:221`, `herdr_slackbot/plugin.py:229`, `herdr_slackbot/plugin.py:249`
- **Problem:** Launch probes the runtime lock, then performs workspace discovery/creation and terminal input without an operation lock or startup reservation. The child takes the instance lock later. Two start actions, or a startup hook overlapping a manual start, can both pass the initial check.
- **Concrete failure scenario:** A barrier reproduction made two launchers observe no workspace. Both returned success, creating **two workspaces and two pane launches**. With an existing workspace, two starts before child lock acquisition submitted the launch command **twice to the same pane**. The second submission can reach an initializing child or remain queued for the shell after that child exits. The existing single-instance test starts with an already-held lock and misses this interval.
- **Suggested fix:** Serialize lifecycle operations across processes and maintain a bounded startup reservation until the child acknowledges its runtime lock or fails. Recheck state under that protection before creating a workspace or writing to a pane. Cover concurrent start/start and start/restart. The runtime lock still prevents two established bridges sharing one state directory; it does not make the launch side effects idempotent.

### 4. Setup can generate a slash command that the preserved configuration will never register

- **Severity:** minor
- **Location:** `herdr_slackbot/setup_cmd.py:129`, `herdr_slackbot/setup_cmd.py:143`, `herdr_slackbot/setup_cmd.py:148`
- **Problem:** `pick()` treats an existing blank identity value as absent and selects the CLI override. `merge_env()` deliberately preserves that blank key. The manifest and printed instructions use the override, while runtime configuration uses its default.
- **Concrete failure scenario:** Begin with `SLASH_COMMAND=` and `BOT_DISPLAY_NAME=` (as in a copied `.env.example`). Run setup with username `me`, command `/herdr-custom`, and display name `Custom`. Reproduction generated `/herdr-custom` / `Custom` in the manifest, kept both blank lines, and loaded `/herdr-me` / `Herdr (me)` at runtime. Slack's installed command therefore has no matching Bolt listener.
- **Suggested fix:** Generate the manifest and instructions from the effective configuration after merging. Preserve existing blank values as promised, and explicitly explain that an override could not be persisted. Test blank existing keys with CLI overrides, including agreement between `run_setup()` output and `load_config()`.
